# 成员3的标注、校准与实验

先用 v2 注册并导出 P02 个人配置。原 P01 资料可回放作为旧系统基线。本轮只完成了代码、合成机制和旧版回归检查，P02 尚无个人实验材料。

## P02 需要保留的材料

1. 初始注册时，每类录 3–5 条独立正例，保存注册 run 和 v2 初始配置 A。每次只录一类、一次动作，停住后结束示范。
2. 录一轮校准试讲，覆盖所选类别的明确指令和无指令的自然讲解。保留摄像头原始视频、轨迹、实际运行配置和标注。网页的轨迹导出保存关键点和事件，原视频另行保存。
3. 从原视频逐条标记意图区间、目标 `gestureId` 和目标 `actionId`。用 run 的媒体毫秒进行对齐。如果用外部相机文件核对，记下原文件时间转换到 run 媒体时间的偏移。直接从该文件逐帧分析时两者起点一致，通常为 0 ms。浏览器录屏的时间不能直接套到 run 上。
4. 人工复核候选错类、错绑定、漏检、重复及自然误触。保留确认依据与片段起止，分别生成配置 B 和 C。冻结后另录独立命令轮与独立自然轮。素材应留出任务末尾的停顿和观察时间，以便系统完成最后一个动作判定。

## 标注文件

下例字段用于描述格式。按该轮录制填写实际时间，从实际配置复制手势 ID，再标记该次意图想执行的功能。若实际绑定与目标功能不同，会列为待复核项。

```json
{
  "version": 1,
  "timeline": "media-ms",
  "complete": true,
  "runId": "从本轮导出的 run 复制",
  "participantId": "P02",
  "rawVideo": {"file": "P02-calibration.mp4", "offsetMs": 0},
  "task": {"kind": "mixed", "startMs": 2000, "endMs": 65000},
  "intentions": [
    {
      "intentId": "intent-01",
      "startMs": 5200,
      "endMs": 5850,
      "gestureId": "从本轮 profile 复制",
      "actionId": "next_page"
    }
  ]
}
```

用途为纯命令轮时用 `command`，纯自然轮用 `natural` 并显式填写 `intentions: []`。有标注缺失时先保留 `complete: false`。`offsetMs` 表示原视频时间加上该偏移得到 run 的媒体时间。任务起止均应在导出的帧时间范围内。

## 模块接口

从 `01_code/custom-gestures/study.mjs` 按 ESM 导入下列函数。可从 Node.js 读取 JSON 后调用，或者由成员2在网页中接到标注和复核界面。新版演示页可手工录制按类的正反例，标注界面尚未接入。

| 函数 | 输入与输出 |
| --- | --- |
| `preflightStudy(run, labels)` | 返回 `{ready, missing}`，检查参与者、来源、轨迹、标注和任务时间，合成来源不能通过真人材料预检。原文件是否齐全仍需核对 |
| `alignIntentions(run, labels, tolerance)` | 返回一对一的 `matched` 与 `review`。在任务区间内优先给每个意图匹配手势和功能都正确的事件，再列出错类 `wrong_class`、绑定不符 `wrong_action`、漏检 `missed`、重复 `duplicate` 和额外触发 `false_trigger` |
| `applyConfirmedReviews(profile, run, labels, decisions, tolerance)` | 由已确认的复核决定生成新 profile。写入父版本、修改记录、来源 run、样例片段、复核及实际参数 |
| `compareProfiles(inputRun, [A, B, C])` | 将每份配置单独放在完全相同的帧上重跑，返回带实际配置、来源、拒绝和逐事件数据的新版 runs |

建议在对照前明确并固定容差。例如 `{earlyMs: 0, lateMs: 350}` 是接口默认值，使用 `event.tMs` 定位。在有重叠的意图区间时函数优先做正确配对，含糊项仍需人工核查。命令成功数按正确配对计，错类、漏检、重复、额外触发分别报告。自然轮误触同时报告任务时长。决定是否执行翻页可以另外看 `actionResult`，容差内识别成功与播放器执行应分别统计。

每条复核决定包含 `reviewId`、`status: 'confirmed'` 和 `kind: 'positive' | 'negative' | 'ignore'`。漏检或错类可为预期手势补正例，须提供人工确认的 `clip: {startMs, endMs}`。已经确认会冒充某类的事件可为该触发类补反例，默认用事件窗口，也可提供手工修正后的片段。若复核发现是相同手势的误绑定，请修改绑定。重复若属于同一真实指令，可标为 `ignore`，避免把真实指令加作反例。调整后在未参与校准的材料上复测。

## 对照实验

A 只含初始正例；B 从 A 加确认补录的正例；C 从 B 加确认的反例。三组固定手势集合、功能绑定、引擎、特征、全局和类别参数以及测试帧。没有确认样例时复用上一组方案。B 与 C 的比较对应反例的增量。示例调用如下。

```js
const tolerance = {earlyMs: 0, lateMs: 350};
const B = positiveDecisions.length
  ? applyConfirmedReviews(A, calibrationRun, calibrationLabels, positiveDecisions, tolerance)
  : A;
const C = negativeDecisions.length
  ? applyConfirmedReviews(B, calibrationRun, calibrationLabels, negativeDecisions, tolerance)
  : B;
const runs = compareProfiles(independentRun, [A, B, C]);
const alignments = runs.map(run =>
  alignIntentions(run, {...independentLabels, runId: run.runId}, tolerance));
```

重放结果的 `source.inputRunId` 应指向标注所属原独立 run，复制标注时仅替换衍生 run 的 ID。比较旧版和新版属于另一个系统对照。用于调参、注册和复核的材料归入开发集，正式指标使用冻结配置后的新数据。需要计算端到端延迟时再记录播放器呈现时间并与人工起手时间对齐。
